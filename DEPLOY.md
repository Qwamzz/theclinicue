# Deploying TheClinicue to Azure

**Target:** Azure App Service (Linux, Python 3.12), served at **https://theclinicue.com**
**Time:** ~25 minutes, most of it waiting for DNS
**Cost:** about \$13/month on B1, or free on F1 without the custom domain

You need: an Azure subscription, the `theclinicue.com` domain, and a GitHub account (`Qwamzz`).


If GitHub asks for a password it wants a **personal access token**: *Settings → Developer settings → Personal access tokens → Tokens (classic)*, tick the `repo` scope, use the token as the password.

> `.gitignore` already excludes the database, `.env`, coverage output and the virtual environment. There are no secrets in the repository — the session key is generated by Azure at provisioning time.

## Step 2 — Provision Azure

### Option A — the script (recommended)

```bash
az login
bash azure-setup.sh
```

It creates the resource group, the Linux App Service plan, the web app, all application settings (including a freshly generated `TC_SECRET_KEY`), the startup command, the health check, HTTPS enforcement and diagnostic logging — then prints your publish profile and the exact DNS records you need.

Override any default with an environment variable:

```bash
APP_NAME=theclinicue-prod LOCATION=uksouth SKU=B1 bash azure-setup.sh
```

### Option B — the portal

1. **Create a resource → Web App**
2. **Basics**
   - Resource group: **Create new** → `theclinicue-rg`
   - Name: `theclinicue` *(this becomes `theclinicue.azurewebsites.net`, so it must be globally unique — add a suffix if it is taken)*
   - Publish: **Code**
   - Runtime stack: **Python 3.12**
   - Operating System: **Linux**
   - Region: **West Europe** (lowest latency to Ghana of the common regions)
   - Pricing plan: **B1** — F1 (free) cannot bind a custom domain
3. **Review + create → Create**, then wait for deployment to finish.

Then, in the new Web App:

4. **Configuration → Application settings → New application setting**, adding each of:

| Name | Value |
|---|---|
| `TC_ENV` | `production` |
| `TC_SECRET_KEY` | run `python -c "import secrets;print(secrets.token_urlsafe(48))"` and paste the result |
| `TC_COOKIE_SECURE` | `true` |
| `TC_SESSION_HOURS` | `8` |
| `TC_BOOKING_HORIZON_DAYS` | `60` |
| `TC_DATABASE_PATH` | `/home/data/theclinicue.sqlite3` |
| `TC_SQLITE_JOURNAL` | `DELETE` |
| `SCM_DO_BUILD_DURING_DEPLOYMENT` | `true` |
| `WEBSITES_ENABLE_APP_SERVICE_STORAGE` | `true` |

   **Save.**

5. **Configuration → General settings**
   - **Startup Command:** `bash startup.sh`
   - **Always on:** On
   - **HTTPS Only:** On
   - **Minimum TLS Version:** 1.2
   - **Save.**

6. **Monitoring → Health check** → Enable → Path `/api/health` → **Save.**

### Why those last two settings matter

`TC_DATABASE_PATH` points inside **`/home`**, which is the only directory Azure App Service keeps across restarts and deployments. Anything written elsewhere is lost the moment the container recycles.

`/home` is an **SMB file share**, and SQLite's WAL journal is not reliable over SMB. `TC_SQLITE_JOURNAL=DELETE` selects the older rollback journal, which is. This is a workaround, not a fix — the fix is technical debt item **TD-01**, migrating to Azure Database for PostgreSQL.

## Step 3 — Wire up GitHub Actions

1. Get the publish profile (the setup script prints it; otherwise): in the portal, on the Web App **Overview** page, click **Download publish profile**.
2. In GitHub: **Settings → Secrets and variables → Actions → New repository secret**
   - Name: `AZURE_WEBAPP_PUBLISH_PROFILE`
   - Value: the entire contents of that file, including the XML declaration.
3. If you changed the app name, edit `.github/workflows/azure-deploy.yml` and update `AZURE_WEBAPP_NAME`.
4. Trigger a deployment:

```bash
git commit --allow-empty -m "Trigger first deployment"
git push
```

Watch it under the repository's **Actions** tab. The `test` job runs first (about 4 minutes: the full suite, the seven-day date matrix and the production configuration check). `deploy` only starts if that passes, and it finishes by smoke-testing the live `/api/health` endpoint.

## Step 5 — Point theclinicue.com at it

### 5.1 DNS records

Add these where the `theclinicue.com` zone is hosted. If you bought the domain through **Azure App Service Domains**, the zone is already in Azure DNS under the same subscription.

| Type | Name | Value |
|---|---|---|
| `TXT` | `asuid` | the domain verification ID (below) |
| `A` | `@` | the app's inbound IP (below) |
| `CNAME` | `www` | `theclinicue.azurewebsites.net` |

Get both values:

```bash
az webapp show -n theclinicue -g theclinicue-rg \
    --query "{verificationId:customDomainVerificationId, ip:inboundIpAddress}" -o table
```

Wait for propagation, then confirm:

```bash
nslookup theclinicue.com
nslookup asuid.theclinicue.com -type=txt
```

### 5.2 Bind the domain

```bash
az webapp config hostname add -g theclinicue-rg --webapp-name theclinicue \
    --hostname theclinicue.com
az webapp config hostname add -g theclinicue-rg --webapp-name theclinicue \
    --hostname www.theclinicue.com
```

Or in the portal: **Custom domains → Add custom domain**.

### 5.3 Free managed TLS certificate

```bash
az webapp config ssl create -g theclinicue-rg --name theclinicue \
    --hostname theclinicue.com
```

Then bind it with the thumbprint it prints:

```bash
az webapp config ssl bind -g theclinicue-rg --name theclinicue \
    --certificate-thumbprint <THUMBPRINT> --ssl-type SNI
```

In the portal this is **Custom domains → Add binding → Create App Service Managed Certificate**.

> The certificate is free and renews automatically. It can only be issued **after** the domain is bound and DNS resolves, so do these in order.

Finally, confirm `https://theclinicue.com/api/health` responds and the padlock is valid.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `Application Error` / HTTP 500 on first load | Startup command not set | **Configuration → General settings → Startup Command** = `bash startup.sh` |
| Logs show `TC_SECRET_KEY must be set in production` | The app setting is missing or empty | Add `TC_SECRET_KEY` in Configuration and **Save** (this refusal is deliberate — see `app/config.py`) |
| Logs show `unable to open database file` | The `/home/data` directory does not exist, or storage is disabled | Confirm `WEBSITES_ENABLE_APP_SERVICE_STORAGE=true`; `startup.sh` creates the directory |
| `database is locked` under load | WAL journal on the SMB share | Set `TC_SQLITE_JOURNAL=DELETE` and restart. Properly fixed by TD-01. |
| `ModuleNotFoundError: flask` | Oryx did not build | Set `SCM_DO_BUILD_DURING_DEPLOYMENT=true`, then redeploy |
| Deploy succeeds but the site 404s | Wrong WSGI target | The callable is `wsgi:app`, not `app:app`; `startup.sh` already handles this |
| Custom domain will not validate | `asuid` TXT record missing or not propagated | Re-check the record; `nslookup asuid.theclinicue.com -type=txt` |
| Certificate creation fails | Domain not bound yet, or DNS not resolving | Bind the hostname first, wait for DNS, then create the certificate |
| Site sleeps and is slow to wake | **Always on** disabled (it is unavailable on F1) | Enable **Always on**; requires B1 or higher |
| Sign-in silently fails | `TC_COOKIE_SECURE=true` over plain HTTP | Enable **HTTPS Only** — the cookie is discarded on an insecure connection |

## Data persistence, honestly

`/home` **is** persistent on App Service, so unlike an ephemeral free tier, bookings survive restarts and redeploys. That is a genuine improvement over the previous plan.

It is still not production-grade:

- SQLite over SMB has slower and less predictable locking than local disk.
- Concurrent writes serialise, and under contention the app returns `503 SERVICE_BUSY` with a `Retry-After` header rather than failing outright.
- There is no automated backup (**TD-12**).

The Technical Debt Register keeps a hard gate: **no real patient data until TD-01 (managed PostgreSQL), TD-02 (schema migrations) and TD-12 (rehearsed backups) have shipped** — release v1.0.1, about 20.5 hours of work.

When you get there, Azure Database for PostgreSQL Flexible Server (Burstable B1ms) is the natural target, and `app/db.py` is the only module that needs to change.

## Alternative: Docker

The `Dockerfile` also works on Azure Container Apps, or any host:

```bash
docker build -t theclinicue .
docker run -d -p 8000:8000 \
  -e TC_SECRET_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(48))')" \
  -e TC_COOKIE_SECURE=true \
  -v theclinicue-data:/data \
  --restart unless-stopped \
  theclinicue
```

The volume mount is what makes the data survive a restart. Put TLS in front of it — `TC_COOKIE_SECURE=true` requires HTTPS.
